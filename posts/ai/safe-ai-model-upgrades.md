# Safe AI Model Upgrades: Regression Evals, Canaries, and Rollback

A newer model improves an aggregate quality score, so the team switches all traffic. Support routing becomes less consistent, JSON refusals increase, latency doubles for long prompts, and the old deployment has already been removed.

A model upgrade is a behavioral software release. The API may remain compatible while decisions, formatting, safety behavior, cost, and latency change.

> **Quick answer:** Pin the current model configuration, run versioned offline regression evals by task slice, verify tool and structured-output contracts, shadow representative traffic where privacy permits, and canary the new version behind a reversible routing flag. Define rollback thresholds before exposure and retain the old path until the observation window closes.

## Inventory the Whole Model Contract

The deployed behavior includes more than a model name:

- provider and exact model or deployment version;
- system instructions and prompt templates;
- sampling and token limits;
- tool definitions and schema versions;
- retrieval, preprocessing, and context construction;
- safety filters and refusal handling;
- retry, timeout, and fallback policies.

Version these inputs together. Comparing two models while silently changing the prompt or retrieval index makes the result hard to attribute and rollback.

Record the effective configuration with each evaluation and production trace using safe identifiers, not complete sensitive prompts.

## Build Regression Cases From Real Failure Modes

Start with representative tasks and known production failures, then add adversarial and boundary cases. Each case should define the input, trusted context, expected properties, allowed variability, and consequence of failure.

```json
{
  "caseId": "support-route-negation-04",
  "slice": "routing-negation",
  "inputRef": "redacted-fixture-184",
  "expected": {
    "decision": "review",
    "allowedQueues": ["review"],
    "mustCiteEvidence": true
  },
  "severity": "high"
}
```

Avoid a dataset made only from happy-path examples generated by the same model. Include ambiguous requests, multilingual inputs, missing context, long inputs, refusals, malicious instructions, and downstream tool failures.

Protect evaluation fixtures like production data. Redact or synthesize sensitive content, preserve provenance, and prevent one tenant's examples from being exposed to another.

## Use Several Gates Instead of One Score

An average can hide a severe regression in a small but important slice. Define hard invariants and quality measures separately:

| Gate | Example |
| --- | --- |
| Contract | Output parses and validates against the supported schema |
| Safety | No unauthorized tool action is proposed or executed |
| Task quality | Correct routing or evidence-backed answer by reviewed rubric |
| Abstention | Insufficient evidence produces review rather than invention |
| Operations | Latency, token use, and error rate remain within budget |

Use deterministic validators where possible. LLM judges can help assess open-ended quality, but calibrate them against human labels, pin judge configuration, and inspect disagreement. A judge model changing at the same time as the candidate invalidates trend comparisons.

Require zero regressions for true invariants. For probabilistic quality, use repeated runs where variance matters and confidence intervals or paired comparisons rather than treating one completion as the model's fixed behavior.

## Test Integration Compatibility

A replacement may support different context limits, tool-call shapes, schema subsets, finish reasons, streaming events, or token accounting. Run consumer contract tests through the real adapter.

Validate:

- missing, extra, null, and reordered structured fields;
- multiple or parallel tool calls;
- refusal and incomplete-response envelopes;
- truncation at configured limits;
- cancellation, timeout, and provider errors;
- retry idempotency before consequential actions;
- rendering of citations, Markdown, and untrusted text.

Do not repair every incompatibility with permissive parsing. That can turn an explicit failure into silent wrong data. [Structured AI Outputs](https://dev.jun-kim.net/2026/09/22/structured-ai-outputs-validate-model-data-before-your-application-uses-it/) explains the deterministic validation boundary that these compatibility tests should preserve.

## Shadow Traffic Without Duplicating Effects

Shadowing sends a copy of eligible production input to the candidate while only the current model's result is served. It reveals real distributions, latency, and cost without directly changing user outcomes.

The shadow path must have no write-capable tools and must not send messages, create tickets, or mutate memory. Apply the same data residency, consent, retention, and access rules as production. Sampling should exclude inputs that policy does not permit for secondary processing.

Compare outputs asynchronously using task-specific evaluators. Do not add candidate latency to the live request. Cap shadow volume and spend, and ensure provider quotas for the current path remain protected.

## Canary With Sticky, Bounded Exposure

After offline and shadow gates pass, route a small cohort to the candidate. Assign consistently by an opaque account or session key so one user does not alternate behavior unpredictably.

Start with low-consequence tasks and exclude workflows whose rollback would be difficult. Increase traffic only after a defined observation window covers enough volume and operational conditions.

Monitor by model version and task slice: accepted outputs, validation failures, abstentions, user corrections, tool-policy rejections, latency, token use, provider errors, and downstream business outcomes. Keep identifiers out of metric labels.

Fallback to the old model is appropriate only before a consequential action and only when the request remains safe to retry. Never run both candidates' side effects and select the preferred result afterward.

## Define Rollback Before Rollout

Write thresholds for automatic stop, operator review, and rollback. Examples include any authorization invariant breach, a sustained schema-failure increase, unacceptable tail latency, or a material regression in a high-severity slice.

Rollback must restore the full configuration bundle, not only the model name. Retain compatible prompts, adapters, schemas, and capacity for the old path. Test the switch under load and audit who can change routing.

If the new model has already written durable memory or generated derived data, model rollback does not undo those effects. Version generated artifacts and plan reconciliation or invalidation.

## Keep Evaluating After Full Rollout

Production distributions drift, providers update infrastructure, and surrounding prompts or retrieval systems change. Continue sampling reviewed outcomes and turning incidents into regression cases.

Compare quality and operations over meaningful time windows, including rare task slices. Re-run the suite whenever the prompt, tool contract, safety policy, retrieval pipeline, or provider version changes.

A safe upgrade is not the model with the highest benchmark number. It is a controlled release whose benefits hold on the application's real tasks and whose failures can be detected, contained, and reversed before they become durable harm.
